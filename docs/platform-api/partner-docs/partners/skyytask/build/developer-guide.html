02 · Authentication & conventions

How every request works

A

Authentication

Authorization: Bearer sp_live_4eC39HqLyjWDarjtT1zdp7dc
  • Server-side only. Never put a secret key in an app, website or repository.
  • Shown once. ShootPortal stores only a fingerprint (hash) of each key.
  • Rotate without downtime. Several keys can be active at once: add the new one, deploy, then revoke the old.
  • Lost or leaked? Tell us; we revoke it immediately and issue a new one.
B

Idempotency (safe retries)

Idempotency-Key: job-10482-create
  • Send a unique key on every POST. Retrying with the same key returns the original result, so a timeout never creates a duplicate project.
  • Keys are remembered for 24 hours.
  • The same key with a different body returns 409 idempotency_conflict.
  • Tip: build keys from your own IDs, e.g. job-<number>-create.
C

IDs, your IDs & metadata

  • Object IDs are prefixed: proj_ rcp_ ctb_ ups_ file_ dlv_ lnk_ evt_. Treat them as opaque strings.
  • Every create accepts your own external_id (unique per object type) and a metadata map of up to 20 string keys.
  • Look up by your ID: GET /v1/projects?external_id=JOB-10482, so you never have to store ours.
D

Lists, limits & request IDs

  • Pagination: ?limit= (max 100) and starting_after=<id>. Responses include has_more.
  • Rate limit: 100 requests/minute per key. Above that you get 429 with Retry-After.
  • Request-Id header on every response. Include it when contacting support.
  • JSON in and out; timestamps are ISO 8601 UTC; sizes are in bytes.
E

Errors

{
  "error": {
    "type": "invalid_request_error",
    "code": "parameter_missing",
    "message": "email is required",
    "param": "email",

04 · Upload sessions & embedding

Open ShootPortal's upload screen inside your app

An upload session is a one-job, one-pilot, short-lived link. Create it on your server, hand the url to your app, and open it. No key ever reaches the phone.

Create a session (server)
POST /v1/upload_sessions
Idempotency-Key: job-10482-ups-1

{ "project": "proj_7f3c…",
  "contributor": "ctb_2c9d…",
  "return_url": "skyytask://jobs/JOB-10482/delivered",
  "expires_in": 86400 }

# 201 Created
{ "id": "ups_2b8e…",
  "url": "https://skyytask.shootportal.app/u/ups_2b8e…?t=…",
  "status": "open",
  "expires_at": "2026-12-16T15:05:00Z" }
A

Session lifecycle

opensubmittedorexpired
  • Valid for up to 24 hours; create a fresh one any time.
  • Uploads go directly to storage in chunks and resume after drops, reloads or app restarts.
  • On submit, the pilot confirms they're finished; you receive delivery.submitted.
  • Then the screen redirects to return_url; on the web it also posts a message.
  • Unused and expired: you get upload_session.expired.
B

Open it in your app

iOS (Swift): in-app Safari view
import SafariServices
let url = URL(string: session.url)!
let vc = SFSafariViewController(url: url)
present(vc, animated: true)
// return_url (skyytask://…) reopens your app when done
Android (Kotlin): Chrome Custom Tabs
CustomTabsIntent.Builder().build()
  .launchUrl(context, Uri.parse(session.url))
// handle skyytask://jobs/… with an intent filter
React Native / Flutter
// React Native: react-native-inappbrowser-reborn
InAppBrowser.open(session.url)
// Flutter: url_launcher, LaunchMode.inAppBrowserView
Web: new window + completion message
const origin = "https://skyytask.shootportal.app";
window.open(session.url, "upload");
addEventListener("message", (e) => {
  if (e.origin !== origin) return;
  if (e.data.type === "shootportal.upload.submitted")
    refreshJob();
});
Use an in-app browser, not a raw web view, for the most reliable file pickers and uploads. Phones pause uploads when the app is backgrounded or the screen locks; they resume automatically on return, and the screen reminds pilots to keep it open. Always treat the webhook as the source of truth, not the redirect.

A

Verify the signature (always)

ShootPortal-Signature: t=1765816802,v1=5f8e0c3a…   # v1 = HMAC-SHA256(secret, t + "." + raw_body), hex
Node.js
import crypto from "node:crypto";
export function verify(rawBody, header, secret) {
  const parts = Object.fromEntries(
    header.split(",").map((p) => p.split("=")));
  if (Math.abs(Date.now() / 1000 - Number(parts.t)) > 300)
    return false; // older than 5 minutes
  const expected = crypto.createHmac("sha256", secret)
    .update(parts.t + "." + rawBody).digest("hex");
  return expected.length === parts.v1.length &&
    crypto.timingSafeEqual(Buffer.from(expected), Buffer.from(parts.v1));
}
Python
import hmac, hashlib, time

def verify(raw_body: bytes, header: str, secret: str) -> bool:
    parts = dict(p.split("=", 1) for p in header.split(","))
    if abs(time.time() - int(parts["t"])) > 300:
        return False  # older than 5 minutes
    signed = parts["t"].encode() + b"." + raw_body
    expected = hmac.new(secret.encode(), signed,
                        hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, parts["v1"])

Respond fast

Return any 2xx within 10 seconds, then do slow work in the background.

Retries for 3 days

1 min, 5 min, 30 min, 2 h, 6 h, then every 12 h. After 3 days of failures the endpoint is paused and we email you.

Ignore duplicates

Delivery is at-least-once. Store each evt_ ID and skip ones you've already handled.

Use the raw request body for verification (before JSON parsing). Your signing secret (whsec_…) is shared once when your endpoint is registered; ask us to send a test event at any time.

07 · Test vs. live & go-live

Build in the sandbox, launch with one key swap

Test mode · sp_test_
  • A complete, isolated copy of your account: projects, uploads, portal and webhooks all work
  • Nothing is ever billed
  • Emails go only to addresses you ask us to allowlist; everything else is held in a log we can share
  • Try the whole flow with fake data, e.g. job JOB-10482, Sam Pilot, Pat Agent
Live mode · sp_live_
  • Real pilots, real clients, real emails
  • Same endpoints, same payloads, same code
  • Test and live data never mix; IDs from one mode don't exist in the other
  • Separate webhook endpoint and signing secret per mode
A

Go-live checklist

☐Keys: secret keys only on your servers, in a secrets manager
☐Idempotency: an Idempotency-Key on every POST, built from your IDs
☐External IDs: your job, client and pilot IDs on every create
☐Upload screen: opens in an in-app browser; return_url handled
☐Real-phone test: a multi-GB upload interrupted and resumed
☐Webhooks: signatures verified on the raw body; duplicates ignored
☐All five events handled, including upload_session.expired
☐Errors: request_id logged; 429 and 5xx retried with backoff
☐Switch: live key and live webhook secret deployed; test data left behind
B

Versioning

The version is in the URL (/v1). Within v1 we only make additive changes: new endpoints, new optional fields, new event types. Write your code to ignore fields and events it doesn't know. Breaking changes would ship as /v2, with advance notice and an overlap period.
